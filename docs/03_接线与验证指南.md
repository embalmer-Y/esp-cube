## 1.1 串口辨认(P4 与 S31 同时接入时)

两块板都接在各自的 **USB-UART 桥接口**(非原生 USB-Serial/JTAG 口):

| 串口 | 桥接芯片 | 归属 | 依据 |
|---|---|---|---|
| `/dev/ttyUSB0` | **CP2102N**(10c4:ea60) | **ESP32-S31 Function CoreBoard-1** | S31 官方原理图注明默认贴 CP2102N-A02-GQFN28 |
| `/dev/ttyACM0` | **CH343**(1a86:55d3) | **P4 板(勿操作)** | P4 v1.52 已取消桥接芯片(原生303A:1001,列表中无);CH343 不在 S31 物料表内 |

烧录/监视一律指定 `-p /dev/ttyUSB0`。

## 3. 编译与烧录

```bash
cd firmware
. ~/esp/esp-idf/export.sh
idf.py --preview set-target esp32s31   # 首次
idf.py menuconfig                      # 填 WiFi SSID/密码(EspCube Configuration 菜单)
idf.py build
idf.py -p <串口> flash monitor          # USB-Serial/JTAG 口
```

首次点亮屏幕若异常:`idf.py menuconfig` → EspCube → LCD pixel clock 改 **40000000**(40MHz),稳定后再提 80MHz。

## 4. 上电验证清单(按序)

**2026-11-08 首次点亮已完成**,日志实测:ES8311 一次点亮(I2C GPIO50/51)、48k 混音器运行、A2DP sink 就绪、WiFi 连接获 IP、SomaFM 电台解码 44.1k 播放(90s 无 underrun/看门狗,断流自动重连 OK)。

**M1.5 解码器攻坚(2026-11-09,用户不在板旁,基于 GitHub issue 调研 + 遥测闭环)**:
1. 调研定位:esp_audio_codec 的 MP3 = 闭源 minimp3 派生(慢+吞帧的根因);S31 汇编库不覆盖 MP3(esp-adf-libs #85);minimp3 上游内存安全问题(#141/#117)对应本项目 SoundHelix 崩溃。
2. 方案:MP3 切换 `chmorgan/esp-libhelix-mp3`(官方 registry 组件,定点解码)。
3. 实测:数据利用率 99.96%(900284/900625B)、音乐占空比 74%(其余为换曲间隙/歌曲安静段)、解码 avg 16ms/帧(余量 1.6×)、零崩溃。
4. 遗留优化:接屏后需复测 LVGL+解码并发(历史教训:LVGL 全帧渲染曾拖慢解码 21 倍);libhelix -O2 编译优化待试。

**M1.7 国内电台源接入(2026-11-09, 真机三族源全部验证)**:
- 调研: 50+ URL curl实测(详见调研报告), 国内主流形态=HLS(95%+), AES加密0%, 用户鉴权墙0%。
- 三大源族真机验证: 蜻蜓FM(ls.qingting.fm, AAC裸段live)✓ / 喜马拉雅(live.xmcdn.com)✓ / CNR卫星拉流(ngcdn001, TS段)✓ —— 全部连续播放、零解码失败。
- 关键坑: 分段AAC帧带**ADTS头(ff f9)**, 解码器必须 `no_adts_header=false`(帧头自带采样率, extractor报0Hz/22050Hz均无碍); 国内平台源多为HE-AAC(核心22050+不发声时), `aac_plus_enable=true` + 连续失败自动翻转SBR的降级链已内置。
- 播放列表已内置4台: 经典947/广东音乐99.3/CNR中国之声/卫星广东音乐(HTTPS经证书bundle)。
- 已知: 直播流无EOS不自动轮播(正确行为), 换台靠UI/AI命令(M2/M3); 国内HLS无ICY元数据, 曲名显示需另行方案(歌词接口/M2 AI播报)。

**M1.6 HLS协议层(2026-11-09)**:
- 集成 `espressif/esp_hls_stream`(extractor 插件模式, **GMF-free**: gmf_pool 仅作 IO 工厂, 帧消费走纯 esp_extractor API)+ `esp_extractor`(TS/MP4/音频ES解复用)。
- 双路径分发: URL 含 `.m3u8` → HLS 会话; 其余 → HTTP/ICY 直连。播放列表轮播逻辑共享。
- 关键坑(实测): ①`file_cfg_init` 仅本地文件(VFS fopen), 网络 URL 必须 `io_cfg_init`+GMF IO 工厂; ②流探测是惰性的——`parse_stream` 后立即 `get_stream_info` 会失败, 必须在**首帧读出后**懒初始化解码器(官方示例同款时序); ③TS/分段里的 AAC 是裸帧, 需 `esp_aac_dec_cfg_t.no_adts_header=true` + 流信息显式配置。
- 验证: 本地 MP3 分段 VOD(19段×4.128s)端到端 → 全程心跳有声, EOS 正确触发轮播; AAC(TS) 路径待真实电台验证。

**M1.5 最终根因(2026-11-09 深夜,遥测实测)**:上述 16-26ms 漂移与"卡顿"的真凶是 **flash 取指争抢**——解码器在 flash 里跑,与 WiFi/BT 争 MSPI 总线,速度随系统负载在 16~27ms 间漂移(所有旧测量都不稳定的原因)。根治:libhelix 源码 vendor 至 `components/mp3_helix`(Apache/RCSL 许可),链接脚本 `(noflash)` 常驻 IRAM → **1.9ms/帧(13.7× 实时余量),缓冲全程钉满 4s**。排查工具链:启用 AUDIO_DEBUG 的 probe(dec_calls/dec_avg)逐级对照。注意事项:①SDK 默认 UI=y,无屏阶段本地 sdkconfig 应关闭;②接屏后必须复测 LVGL+IRAM 解码并发(余量 13× 理论无碍)。

**上电调试中解决的关键问题(记录供复现)**:

| 问题 | 根因 | 修复 |
|---|---|---|
| SPI 私有TX缓冲分配失败(显示黑屏) | 每笔传输从内部DMA堆临时分配bounce, BT/WiFi启动后内存碎片化 | `io_cfg.flags.psram_dma_direct=1` 走 PSRAM 直接DMA(零拷贝) |
| 蓝牙使能后整机静默挂死 | 控制器模式choice默认BLE_ONLY,而代码按双模使能 | `CONFIG_BTDM_CTRL_MODE_BR_EDR_ONLY=y` + `esp_bt_controller_enable(ESP_BT_MODE_CLASSIC_BT)` |
| 开机即崩溃(strnlen(NULL)) | 事件总线全量派发,UI回调未过滤事件类型,data=NULL | 回调内按事件ID过滤(总线按类型订阅列为TODO) |
| MP3 解码周期性 "Not supported format" | 跨网络读块的半帧被丢弃 + ICY元数据后数据被丢 | 解码pending缓冲 + ICY零丢弃状态机 |
| IDLE/主任务饿死 | esp_lvgl_port v2.9 任务参数在结构体(Kconfig无效) | `lvgl_port_cfg_t.task_affinity=1` 等结构体配置 |

| 步骤 | 现象 | 不对时排查 |
|---|---|---|
| 1 启动日志 | `ES8311 ready: 48000Hz/2ch` 且无 I2C 报错 | I2C 超时 → 核对音频引脚(已核实为 50/51) |
| 2 屏幕点亮 | "EspCube" 深色页 + 立方体旋转 + 频谱 | 黑屏 → 亮度命令;花屏 → `swap_bytes`;降时钟重试 |
| 3 WiFi | 日志 `got ip` | 查 SSID/密码(Kconfig) |
| 4 网络电台 | 喇叭出声,UI 显示 StreamTitle | 无声 → `player` 日志;确认喇叭+音量 |
| 5 蓝牙 | 手机搜到 "EspCube"(媒体音频),播放出声 | 搜不到 → 手机选媒体音频;变速/断续 → 调 `ESP_CUBE_BT_SRC_RATE` |
| 6 UI 频谱 | 柱状随音乐跳动 | 不动 → mixer 频谱抽头日志 |
