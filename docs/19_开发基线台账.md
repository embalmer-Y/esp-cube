## 23. 执行记录(批次 18: T15 首段——SRP-6a 自实现 + 配对服务宿主侧, 2026-11-13)

**改动**: 新组件 `firmware/components/pair`(L3, 已登记层表) 7 文件 + 工具 3 件 + 套件接入。

3. **srp6a**(src/srp6a.h/.c): 服务器/客户端双角色。协议档自定义并写入头注: k=3(RFC 2945 经典), H=SHA-256, K=H(S), x=H(s|H(user:pin))(RFC 2945), M1=H(H(N)^H(g)|H(user)|s|A|B|K), M2=H(A|M1|K); A/B=384B 定长大端且 **<N 正规性档**(≥N 拒绝, 免除法); M1 恒时比较。密码学经 srp_port 注入(目标=PSA+esp_random, 宿主=独立 mini-sha256+urandom)。

6. **过程缺陷(3 处真实实现缺陷, 全被差分/负例逼出)**:
   - `ubn_sub` 别名自毁: `r->n = 0` 先于读 `a->n`, 而 `ubn_sub(&x,&x,m)` 别名调用使循环界变 0 —— 循环界先取局部。
   - `mont_mul` p[] 清零不足: 只清 pn(=a.n+b.n) 而 REDC 触达 p[0..2n], 短操作数时 p[pn+1..2n] **残留上次调用栈垃圾**跨调用污染(症状=结果含三角形数 T(a)·R 特征)。
   - 传播循环 u32 回卷: `p[idx] + (uint32_t)k` 两个 u32 相加在赋给 u64 **之前**回卷, 进位位丢失 —— `(uint64_t)p[idx] + k`。
   **教训**: 差分对拍必须覆盖多 limb 操作数与跨调用序列(单 limb 全过≠正确); 探针基准自身也要过审查——两度被参考实现的 `a += a` 溢出(m≈2^64 时倍增回卷)误导, 浪费数轮排查; "C 与 Python 不一致"时先仲裁基准再怀疑实现。

### 52.2 根因链（逐环实证）

1. esp_lvgl_port(lvgl9) 以 `xTaskCreatePinnedToCoreWithCaps(..., MALLOC_CAP_INTERNAL|MALLOC_CAP_DEFAULT)` 创建 taskLVGL（esp_lvgl_port.c:84-88; app_ui.c 未设 task_stack_caps 走默认）。
2. P4 的 MALLOC_CAP_INTERNAL 堆含 RTCRAM 区（heap/port/esp32p4/memory_layout.c: caps=INTERNAL|EXEC, 0x50108000 起 31KB; 注册序 DRAM 区在前）。taskLVGL 24KB 栈（CUBE_TASK_LVGL_STACK）落入 RTC RAM——几何证据: RTCRAM 结构中栈顶 0x5010e36c, 跨度 0x5F7C≈24KB; PIE 缓冲区 0x501083f0 恰在栈底上方。
3. esp_efc_codec(P4 预编译库)用 PIE 向量协处理器解码; taskLVGL 为常驻 PIE owner。FreeRTOS 将 PIE 上下文保存区 carve 在**任务自己的栈底**（port.c pxPortGetCoprocArea）→ 保存区随栈落入 RTC RAM。
4. **PIE 向量存储指令(esp.vst.128)不能写 LP SRAM** → 保存即 Store access fault。平时不触发: taskLVGL 为唯一 owner 时 pxPortUpdateCoprocOwner 返回 -1 不做保存。
5. 触发条件=任何其他任务首次执行 PIE 指令→owner 交接→保存 taskLVGL 的 PIE 状态→fault→双核 panic 级联→无调试器时 HP_SYS_HP_WDT 复位（rst:0x7）。实证 **6/6**（5×CLI faceperf start + 1×本 JTAG 注入, 皆 ~1.6-1.8s 后）。路径: faceperf start → CLI 任务内 lv_efc_set_src_data 同步解码第 0 帧 → CLI 在 cpu1 首次用 PIE → 交接 → 保存 → fault。
6. 佐证: 内部 RAM(0x4ff00000-0x4ffc0000)全扫 PIE 缓冲区指针零命中（保存区头随栈在 RTC RAM, 不在内部 RAM）; fault 区域 vst 写入零落盘（内容仍 0xa5a5a5a5 栈填充）。

### 52.3 修复（本批实施, 板验待烧录）

- **修复 A**: `CONFIG_ESP_SYSTEM_ALLOW_RTC_FAST_MEM_AS_HEAP=n`（defaults.esp32p4 + 本地 p4c5）→ RTCRAM 退出堆, MALLOC_CAP_INTERNAL 栈只能落 HP SRAM。风险: 若 LVGL 初始化时 HP SRAM 无 24KB 连续块, taskLVGL 创建会失败（boot 日志可见 "Create LVGL task fail!"）→ 届时再降栈或腾挪。烧录后必须核对。

### 52.8 一小时回归结果 + "59 分钟网络失效"根因闭环（2026-11-18 14:10）

**回归窗**: 13:09:31–14:09:32（v5 固件 f1d0482f, 串口 ACM1+ping 双轨）。
**串口**: 全窗 1 次复位（窗首 reset run 起点）, 零 panic/abort/Guru（3 处 "abort" 字样=esp-tls 重连 errno 字符串, 非崩溃）。**表情/内存/任务全部稳定 59 分钟。**
**ping**: 346 次 OK, 14:08:06 起 11 次超时——即下述网络失效。

**根因链（日志 871 行签名, 与 F0 run3 构成 2/2 复现）**:
1. `soul: bh radio_start (boredom)` @3502927ms(58.4min)——soul 无聊点火开电台（两次"59 分钟"的巧合=无聊计时阈值, 非时间退化）。
2. HLS 管线启动（playlist→TLS→segment）瞬时挤兑内部 DMA 池。
3. `eh_sdio: dma_alloc(7680) failed; dropping read` @3505842——hosted RX 7.5KB DMA 分配失败。
4. eh_sdio 掉读后**无恢复路径**→传输层永久死亡→ping 全超时（设备存活, 电台静默重试）。
5. 堆总量全程平坦（30576199→30573847, 58min Δ2.4KB）——**非全局泄漏**; 失效瞬间 -2MB=HLS 管线拆除重建。

**结论**: 任务 1 的"Wi-Fi 失效未定因观察"升级为**可复现软件问题**（触发器=soul 无聊开电台, 可按需复现无需等 59min）。v5 修复范围（PIE/表情）不涉及本问题——非 v5 回归。

**修复方向（待排期）**: (a) HLS/TLS/HTTP 接收缓冲去内部化（mbedtls IO/esp_http_client/GMF 块 caps→PSRAM）, 削平启动尖峰; (b) esp_hosted RX 分配失败改为重试退避而非掉读死; (c) 近期规避: soul 无聊开电台前检查网络健康/预热缓冲。
